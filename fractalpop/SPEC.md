# fractalpop — a lightweight code highlighter

Fractalpop is a lightweight syntax highlighting for JavaScript, Typescript, popular programming languages, and formats commonly generated by coding agents, **and most importantly** for Svelte, Sveltekit, .svx, and SASS. It runs in browsers and JavaScript runtimes and returns HTML without requiring a DOM.

---

## 1. Explicit Goals

Two, in order of importance:

1. **Indented pure Sass** (single-tab, no braces, no semicolons). This is a non-negotiable target.
2. **Svelte / SvelteKit integration.&#x20;**Which includes markdown in Sveltekit, and `.svx` (svelte equivalent to `.mdx`). Many general highlighters assume React or a DOM and don't drop cleanly into SvelteKit SSR + `.svelte` / `.svx` files. fractalpop does.

Everything else - the general language pack (TS, CSS, Python, SQL, Ruby, Lua, …), themes, line highlighting, remark/mdsvex adapters - is standard highlighter surface we ship so the package is complete.

---

## 2. Goals

- Return **HTML strings** from source without touching the DOM - runs in browsers, Node, edge, and at **build time / SSR**. Because there's no DOM and no randomness, server-rendered and client-rendered markup are identical → **no SvelteKit hydration mismatch**.
- Highlight **indented Sass** correctly (§6). First-class, thoroughly tested.
- Integrate first-class with **Svelte / SvelteKit**: a component, an action, and `.svelte` composite-file highlighting (§7).
- Highlight code fences in **`.md`, `.mdx`, and `.svx`** on any framework, via thin adapters over the same core (§8).
- **Theming through CSS variables** (`--fp-<type>`) - themes are plain CSS the consumer drops in, compatible with any CSS setup (vanilla, Tailwind, scoped Svelte styles). No JS theme runtime required.
- **Line highlighting** and per-token / per-line marking.
- Ship a **general language pack** so it works as a normal highlighter anywhere (React, plain HTML, etc.).
- **Blazing fast**: single-pass lexers, string-concat fast path, tree-shakeable per-language modules, tiny core.
- Optional **GPU path** (`gpu-lexer`) for async, language-agnostic highlighting of dynamic/unknown/mixed-region code (§12).

## 3. Public API

```ts
import { highlight } from 'fractalpop'

const html = highlight(code, {
  lang: 'sass',            // resolved via id / extension / alias; default 'typescript'
  config,                  // optional explicit parse config — overrides the registry
  cx,                      // Partial<Record<TokenType, string>> — extra class per token type
  mark,                    // (token) => void — mutate one token (class/style/data-*)
  markLine,                // (line) => void  — mutate one line (used for line highlighting)
})
```

- Returns a **string**. Caller wraps in `<pre><code>` (the Svelte component and adapters do this for you).
- `cx` / `mark` / `markLine` are the only customization hooks. **Pass none of them and `render` takes a fast path**: straight string concatenation, no per-token object allocation. Pass any and it switches to the object-building path that runs your hooks. This is the single most important perf lever.
- Lower-level entry `fractalpop/core` exports `parse()`, `tokenize()`, `render()` (→ string), and `generate()` (→ hast-like AST). Adapters that live in a unified/hast pipeline (remark) consume `generate()`, not `render()`.

### 3.1 Entry points

| Import | What you get |
|---|---|
| `fractalpop` | **TypeScript + plaintext only** by default. Tiny bundle; register more languages yourself. |
| `fractalpop/full` | All 32 languages registered up front. Drop-in replacement for the old default `fractalpop`. |
| `fractalpop/core` | `parse`, `tokenize`, `render`, `generate` — no language registration. |
| `fractalpop/lang` | Language metadata registry (`lang`, `findLanguage`, `allLanguages`). |
| `fractalpop/lang/*` | Individual language configs (tree-shakeable). |
| `fractalpop/gpu` | Async WebGPU path via optional peer `gpu-lexer`. |

### 3.2 Registry utilities

```ts
import {
  registerLanguage,
  setDefaults,
  importDefaults,
  canonicalizeLang,
} from 'fractalpop'

registerLanguage({ id: 'python', extension: 'py', aliases: ['python3'] }, pythonConfig)
setDefaults({ python: pythonConfig, rust: rustConfig })
await importDefaults(['python', 'rust'])
canonicalizeLang('tsx') // 'typescript'
```

- `registerLanguage(language, config?)` adds one language to the registry.
- `setDefaults(languagesOrConfigs)` replaces the default set. Accepts either `Language[]` or `Record<string, ParseOptions>`.
- `importDefaults(ids)` asynchronously imports and registers languages by id.
- `canonicalizeLang(name)` resolves a name/alias/extension to the canonical language id.

## 4. Engine architecture

Three pure stages:

```
source ──tokenize──▶ [ [type,value], … ] ──assemble──▶ { value, lines[] } ──render──▶ HTML string
                                                                          └▶ generate──▶ AST (for remark)
```

### 4.1 Token types = the theming surface
A fixed, ordered list of token types. **This list matters because it *is* the theming contract**: every token renders `class="fp__token--<type>"` and `style="color:var(--fp-<type>)"`, so each type maps to exactly one CSS variable a theme can set. Keep the list small and stable so themes stay portable.

```
identifier keyword string class property entity sign comment break space   (+ jsxliterals for JS)
```

During lexing these are **numeric indices** (fast `Set`/array work); the string names are resolved only at render. `break` = newline, `space` = horizontal whitespace run — both preserved so output is whitespace-faithful and line-splitting is exact.

### 4.2 `tokenize(code, options)` — general lexer
Single left-to-right scan. Per position, in priority order: comment (`onCommentStart`/`onCommentEnd`) → literal (`onLiteral`, e.g. hex colors) → quotes/strings → newline → whitespace → word (classified via `keywords`/`typeKeywords` Sets, `.`-preceded → property, Capitalized/number → class, else identifier) → sign (punctuation `Set`) → fallback.

A language config is: `keywords`, `typeKeywords`, `onCommentStart/End`, `onLiteral`, `onQuote`, `caseInsensitive`, and the key escape hatch — a full **`tokenize(code, options)` override**. Complex languages (CSS, **Sass**, Svelte) run the plain lexer and then **post-process the token array**; this is exactly how the reference's CSS preset rejoins `--dashed-names` and distinguishes declarations from nested selectors.

### 4.3 `assemble` → lines
Splits the flat token stream into `lines[]` (`{ index, value, tokens[], annotations[] }`), handling tokens whose value contains embedded newlines. Per-line structure is what makes **line highlighting** a one-liner: `markLine` adds a class when a line index is in the highlight set.

### 4.4 `render` (string) and `generate` (AST)

- `render` fast path (no hooks): concat `<span class="fp__line">` per line, `<span class="fp__token--<type>" style="color:var(--fp-<type>)">` per token, HTML-encoded.
- `render` hook path: builds mutable token/line objects, runs `cx`/`mark`/`markLine`, serializes.
- `generate` returns AST nodes (element/text) so the remark adapter can splice highlighted code into the mdast→hast tree instead of injecting a raw string.

*Author language: TypeScript throughout. TS compiles away — runtime is identical to hand-written JS; we get types for the config and hook signatures. Built with `bunchee` (same as the reference's TS packages).*

## 5. Languages

**Ours to build with real effort:** `sass` (indented — §6), plus the day-one authoring set **`typescript`** (incl. `tsx`), **`css`**, **`scss`**, and **`svelte`** (composite — §7).

**General pack (breadth, ported incrementally):** javascript, python, c, cpp, csharp, go, java, rust, json, diff, shell, sql, html, yaml, markdown, plaintext, ruby, kotlin, swift, php, toml, powershell, dockerfile, graphql, hcl, zig, lua.

Registry: metadata (`{ id, extension, aliases[] }`) and parse configs live in **separate mutable registries** (`lang-registry.ts` + `lang-configs.ts`), keyed by every id/extension/alias, with duplicate detection on registration and normalized lookups (`trim().toLowerCase().replace(/^\./,'')`). The default `fractalpop` entry registers only TypeScript + plaintext; `fractalpop/full` registers all 32. Each language config is a separate module under `fractalpop/lang/*` so bundlers tree-shake unused ones, and `registerLanguage` / `setDefaults` / `importDefaults` let consumers build their own set.

> **Breadth strategy:** the deterministic general presets are ported as needed (they're small). The **GPU path (§12) covers the long tail** of general/unknown/mixed languages for free, so we don't have to hand-write every grammar to be a credible general highlighter. Our hand-written effort stays on TS/CSS/SCSS/**Sass**/Svelte.

## 6. Indented Sass - the core feature

Curly-brace languages (CSS, SCSS) track structure with `{ } ;`. **Indented Sass has none of that** — structure is entirely indentation. So the Sass preset is a **line-oriented tokenizer** (a custom `tokenize`): classify each line from its indent + leading token, then lex its content and re-tag.

### 6.1 What must be colored

```sass
// line comment                      → comment
/* block comment */                  → comment
$brand: hsl(212, 90%, 55%)           → property($brand)  sign(:)  value…
.card                                → class (selector)
  color: $brand                      → property(color) sign(:) property($brand)
  &:hover                            → sign(&) + pseudo selector
    background: darken($brand, 10%)  → property + entity(darken) call
@mixin card($pad: 1rem)              → keyword(@mixin) entity(card) property($pad)
+card / =card                        → indented-syntax include / define → sign + entity
@include card(2rem)                  → keyword(@include) entity(card)
@if $x > 0 / @each $i in $list       → keyword + operators
%placeholder                         → class (placeholder selector)
#{ $expr }                           → interpolation: signs + inner expression lexed normally
```

### 6.2 Algorithm

1. Split into physical lines; leading-whitespace run = indent. **Detect the indent unit** from the first indented line (tab, or N spaces) rather than assuming single-tab - real `.sass` uses both. `depth = indentWidth / unit`.
2. Track open block-comment state across lines.
3. **Classify each line** by leading token:
   - `//` or `/*` → comment.
   - `$name` with a top-level `:` → **variable declaration** (`$name` = property, RHS = value).
   - `@word` → **at-rule / control** (`@mixin @include @function @if @else @each @for @while @use @forward @import @extend @content @return @media @supports …`) → keyword; the name after `@mixin`/`@function`/`@include` → entity.
   - `=name` → mixin **define** (indented shorthand); `+name` → mixin **include** → sign + entity.
   - `%name` → placeholder selector → class.
   - selector-shaped (`. # & % :` sigils, element names, combinators `> + ~`, **and/or a deeper-indented child line follows**) → **selector line**.
   - `word: value` shape with a non-empty RHS and no deeper declaration children → **declaration**.
4. **The colon problem (no braces to help):** a `:` is a *declaration* colon when it's `word: value` with a value to end-of-line and the line isn't a selector with nested children; it's a *pseudo-selector* colon (`:hover`, `::before`) when immediately followed by an identifier with no space on a selector line. **Lookahead at the next line's indent** disambiguates the hard cases (a selector has deeper-indented children; a bare declaration does not).
5. **Value lexing** (shared with SCSS): numbers + units (`px em rem % vw deg s ms fr`), hex colors, `$vars`, function calls (name before `(` → entity), operators (`+ - * / %`), commas, `!default !global !important`, booleans/`null`.

### 6.3 Shared value module
Factor value-lexing into one helper imported by **both `sass.js` and `scss.js`**, so the two dialects differ *only* in structure detection (indent vs braces), not value coloring. SCSS structure detection reuses the reference CSS approach (brace/semicolon block tracking, `opensBlock` lookahead, dashed-name rejoin) extended with `$vars`, `@`-rules, `&`, `#{}`, `%placeholder`, `//` comments.

> Highest-risk module → its own fixture suite (§10): deep nesting, `&` chains, `@each`/`@if`, interpolated selectors, multiline maps, `!default`, `=`/`+` shorthand, and the colon/indent edge cases.

## 7. `@fractalpop/svelte`

The Svelte/SvelteKit integration. Analogous to the reference's React package, built with `bunchee`, `svelte-package` output, `svelte` export condition, depends on `fractalpop`.

### 7.1 Component (Svelte 5 runes)

```svelte
<script lang="ts">
  import { Highlight } from '@fractalpop/svelte'
  let { code, lang = 'sass', highlightLines = [] } = $props()
</script>

<Highlight {code} {lang} {highlightLines} />
```

- Calls `highlight(code, { lang, markLine })`, injects via `{@html}` (engine output is HTML-encoded → safe). Renders `<pre class="fp"><code>…</code></pre>`.
- **Zero client JS** for the common case: the string is produced in SSR/build and shipped as static HTML — nothing to hydrate.
- Props: `code`, `lang`, `highlightLines` (→ `markLine` adds `fp__line--highlighted`), `cx`, `class`/`style`/`preClass`/`codeClass` passthrough.
- Component ships **no `<style>` block** (consumers bring theme CSS via `--fp-*`).

### 7.2 Action (dynamic / client-side code)

```svelte
<pre use:fractalpop={{ lang: 'ts' }}>{code}</pre>
```

Highlights the element's text on the client — for snippets you don't have at build time.

### 7.3 `.svelte` composite highlighting
A `.svelte` file is **TS in `<script>` + markup with `{expr}`/`{#if}`/`{@render}` + CSS/Sass/SCSS in `<style lang="…">`**. The `svelte` language config runs a region splitter, then delegates each region to the matching preset — crucially, `<style lang="sass">` goes to **our own Sass preset**, so a Svelte component's indented-Sass block highlights with the same engine, no external grammar. Markup lexer handles tags/attributes and delegates `{…}` expressions to the TS lexer. (For messy/edge cases, the GPU path is the fallback — §12.)

## 8. Doc adapters — md, mdx, mdsvex

The core is framework-agnostic, so adapters are thin and all emit the **same `fp__token--*` / `--fp-*` markup** → one theme CSS styles code everywhere, regardless of source format or framework.

### 8.1 `@fractalpop/remark` — covers `.md` **and** `.mdx`
A remark plugin (like the reference's) that walks the tree with `unist-util-map`, matches code nodes (`type === 'code'`), reads fence lang + meta, calls `generate()`, and replaces the node with `<pre><code>` hast (via `data.hName/hProperties/hChildren`). **MDX needs no separate package** — MDX code fences are the *same* mdast `code` nodes as Markdown, so this one plugin serves both. Parses fence meta `{1,3-5}` → line highlighting (`fp__line--highlighted`); normalizes aliases through the registry. Works anywhere unified/remark runs (Next MDX, Astro, Docusaurus, plain remark).

### 8.2 `@fractalpop/mdsvex` — `.svx`
mdsvex highlights through its own `highlight.highlighter(code, lang, meta) => string` hook, which is why it needs a dedicated adapter (different surface than remark):

```js
// svelte.config.js
import { fractalpopHighlighter } from '@fractalpop/mdsvex'
mdsvex({ highlight: { highlighter: fractalpopHighlighter } })
```

Returns the HTML string and **escapes Svelte-significant chars** (`{`, `}`, `` ` ``) so highlighted code isn't reparsed as Svelte markup — the classic mdsvex footgun, handled here. Parses fence meta for line highlighting.

**Package count:** `fractalpop` (core+languages), `@fractalpop/svelte`, `@fractalpop/remark` (md+mdx), `@fractalpop/mdsvex`. Optional `@fractalpop/themes`. **No standalone mdx package.**

## 9. Theming

- Token color = `var(--fp-<type>)`; line/emphasis via classes (`.fp__line--highlighted`).
- A theme = a CSS block setting `--fp-identifier`, `--fp-keyword`, `--fp-string`, `--fp-class`, `--fp-property`, `--fp-entity`, `--fp-sign`, `--fp-comment`, … . Drop-in, CSS-var compatible with any setup; dark/light = swap the var block under a selector/media query.
- `cx` appends utility classes per token type for emphasis (`cx:{ keyword:'font-bold', comment:'italic opacity-70' }`) — Tailwind-friendly without writing selectors.
- Optional `@fractalpop/themes`: a couple of reference light/dark themes as importable CSS + a copyable docs page.

## 12. GPU path — `fractalpop/gpu` (complementary)

`gpu-lexer` splits source into parts (words/whitespace/newlines/symbols) and a tiny WebGPU model labels each part from surrounding context — **language-agnostic**, \~**88% token-label match vs Shiki**, \~4ms/file, and it already handles **mixed-language files including embedded `<script>`/`<style>` in Svelte, Vue, and HTML**. That's exactly our hardest deterministic case, so it's a real second path, not a toy — but it's **complementary, not the default**, because it's WebGPU-only, async, approximate, and needs a one-time model load (can't run at build/SSR).

| | Deterministic (default) | GPU (`fractalpop/gpu`) |
|---|---|---|
| Runs at build/SSR | ✅ | ❌ (WebGPU, client, async) |
| API | sync `highlight()` | async `await highlight()` |
| Accuracy | exact | \~88% vs Shiki |
| Language | explicit `lang` | inferred; unknown/mixed OK |
| Best for | SASS, Svelte SSR, exact themes, tiny bundles | client-side dynamic/pasted code, unknown languages, general-pack long tail, brittle composite files |

- Optional peer dependency; importing any non-GPU entry never loads the model. Same `fp__token--*` output → identical theming/`cx`/`mark`.
- Validate on our own **Sass/Svelte** corpus before trusting it there — 88% *average* is not 88% *on indented Sass*.
